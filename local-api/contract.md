# Shared local API contract

This file is the self-contained v1 authoring and operator contract for the shared Delphi local evaluator. It does not depend on a downstream Project Foundation module or migration TODO. The Go implementation is standard-library-only and has no HTTP, IAM, preview, review-approval, or publication authority.

## Context and trust boundary

The public `local-api/run` launcher is identity-only. Configure exactly one API-owned state directory in the ignored, private `local-api/private-context.json` (`{"schema_version":"1","state_root":"/absolute/private/path"}`); it must already exist outside the Project checkout. Invoke Project operations from the selected Project Git checkout. The launcher resolves the registered Project's stored binding and rejects a checkout mismatch; for an unregistered Project it uses only Delphi's managed `foundation_documentation` convention. There is no caller-selectable Foundation or state path, path map, sibling scan, or alternative fallback. `builder-project list` is global and does not require a Project checkout. Normal `context` returns a local authoring destination and identities only. Its private evaluator adaptation is not public output and must not be sent to a browser/catalog.

That `context` path response (including its legacy authoring `next_action`) is provisional local behavior, not the authoring contract or a planned remote API shape. Project artifact skills write their standard relative files in the selected Project's own authoritative Foundation; they do not consume an API-returned destination. The API provides status, registration and synchronization evidence, not a write location. A status `go` or matching Project ID alone does not show that a private binding read the same Git authority: the unregistered standard convention is sufficient only when it is the selected authoritative Foundation and no different private binding applies. Otherwise require independently matchable source identity/revision/digest evidence if exposed; when unavailable or mismatched, report API verification `unverifiable` with TEACH and do not claim Builder admission or redirect writes. Company/default Design System selection remains readable, but authoring those owner levels is outside the current Project-owned skill contract. No remote API is implemented by this local command.

The internal evaluator CLI retains explicit roots and bindings for package tests and the launcher adapter; these are not public `local-api/run` options. This distinction keeps the evaluator behavior and committed Design System pins intact while API context owns the binding selection.

Internal evaluator commands receive an explicit existing absolute host `--workspace-root`, workspace-relative `--project-root`, workspace-relative `--foundation-root`, and `--project-id`. `--project-root .` selects the workspace itself. Design System also requires `--company-id`; an explicit workspace-relative `--source-bindings` selects configured Project/Company/default inheritance. When no binding file is configured, the evaluator derives only the standard Project source (`design/system/design-system.json`) in memory for working-tree evaluation. This does not create or require a Project config file. Committed mode still requires explicit pins and fails without them. `--default-owner-id` is required if a configured default slot is non-null, even when another slot wins. IDs use `[a-z][a-z0-9-]{0,63}`.

Roots and relative paths reject traversal, control characters, reserved `.git` segments, and existing symlink components. The caller's cwd is irrelevant. Foundation and selected Company/default repositories must stay inside the explicit workspace. All three Knowledge operations require Foundation to be exactly its Git top-level checkout. Git object reads ignore replacement refs so a full revision always names its literal committed object. The launcher CSV-quotes Docker mount fields, mounts the workspace read-only at `/workspace` and the module read-only at `/delphi-local-api`, and only `record-review` overlays its selected Foundation writable. That writable root cannot be the workspace, Project root, or an ancestor of Project/shared implementation. Workspace visibility is trusted local execution, not a security sandbox or authentication.

All supplied binding identities must match the explicit Project/Company context. This is an operator assertion, not proof of ownership or IAM authorization. Private bindings are input-only and never appear in output or diagnostics. Project → Company → default chooses one whole Design System source; a broken selected source never falls back, and unselected source contents are not opened.

## Prototype v3 authoring contract

`prototypes/catalog.json` is an exact JSON object with `schema_version: "3"`, the explicit `project_id`, and a nonnull `prototypes` array (maximum 256 records; empty is valid). Each record has exactly `id`, `name`, `description`, `root`, and `status`. Status is `active|archived`; both are inventoried and returned. IDs are stable; name is 1–160 Unicode characters, description is null or at most 2,000 characters, and root is one direct child directory under `prototypes/`. The catalog, every manifest, and the evaluator response use schema version 3 as one cutover; no v2 reader is provided.

Every `<root>/prototype.json` has exactly `schema_version`, `id`, `authoring_mode`, `entry_point`, `screens`, `sources`, `assets`, `transitions`, `scenarios`, `related`, and `design_system_ref`. `schema_version` is `"3"`; mode is `image_first|design_system_first`. Required arrays are nonnull, including `scenarios`, which may be `[]`. `entry_point` must equal one declared Screen path, ensuring the default entry and viewer selection identify the same Screen. `design_system_ref` is null or exactly `{id, content_digest}`; the full lowercase SHA-256 digest names the provider's complete inventory digest, not its raw definition digest.

Each Screen is exactly `{id,name,path,scope,default_state_id,states}` with explicit `scope:null` and at least one State. Screen IDs/paths are unique. Each State is exactly `{id,name,identifier_image,approved_references}`; IDs are unique within that Screen, and `default_state_id` must match one nested State. Identifier images are safe Prototype-relative raster image paths and must be declared assets. A State's optional `approved_references` contain rows exactly `{id,image,approval_evidence}`; reference IDs are unique within the State, images must be declared raster assets, and evidence paths must also occur in `related`. This is structural evidence only: the evaluator does not determine human approval or inspect image bytes/fidelity.

Each Transition is exactly `{from_screen_id,from_state_id,action,to_screen_id,to_state_id}`. Both endpoint pairs must identify declared Screen/State entries. Action is a 1–160 character label and the directed tuple is unique. State IDs are scoped to their Screen; the viewer combines the Screen path with `?prototype_state=<state-id>` so states do not need separate HTML files. Each Scenario is exactly `{id,name,steps}` with a stable unique Prototype-local ID, a 1–160 character name, and a nonempty ordered list of exact `{screen_id,state_id}` pairs. Repeated pairs and adjacent steps without a declared product Transition are valid. A Prototype admits at most 256 scenarios and 4,096 total steps. Each Related record is exactly `{kind,path}`; kind is `todo`, `decision`, or `documentation`, and path is safe Foundation-root-relative regular evidence. Related evidence is not authorization.

The evaluator inventories every file/directory under the managed collection, rejects unregistered roots, orphan directories, undeclared or unsafe files, and returns all-or-nothing. Draft explorations belong outside the managed collection. Shared limits remain 1,024-byte paths, 2,048 files, 2 MiB per file, 64 MiB aggregate, 256 Screens, 1,024 States, 4,096 Transitions, 256 Scenarios, 4,096 total Scenario steps, 256 approved references, and 64 Related records. UTF-8 paths are compared byte-for-byte. Items and diagnostics are sorted.

The inventory hash encoding remains SHA-256 over ASCII `builder-artifact-inventory-v1`, NUL, followed by sorted source-ID/path records and each file's raw content hash; include catalog, each manifest, and declared sources/assets. The unchanged encoding is not a schema compatibility reader. The complete response uses `schema_version: "3"`, includes each item's `status`, `authoring_mode`, Screens/States, transitions, and nonnull scenarios, and retains explicit project, mode, revision, all-or-nothing digest/items, diagnostics, and `design_system_validation: "not_evaluated"`. Structural `go` proves neither rendering, image fidelity, navigation, actual Design System usage, human approval, QA nor publication.

## Design System v1 source and definition

The caller supplies `--source-bindings`, a strict JSON file no larger than 64 KiB. It has exactly `schema_version`, `project_id`, `company_id`, and `sources`; schema version is `"1"`, identities match command context, and `sources` has exactly the three required nullable slots `project`, `company`, and `default`. Each non-null binding has exactly `repository_id`, `checkout_root`, `revision`, and `definition_path`. Repository IDs use the stable ID grammar. Checkout roots are workspace-relative exact Git roots without symlink components; a Project binding must equal the selected Foundation root. Definition paths are safe Git-relative paths ending in `design-system.json`, beneath the repository root.

Working-tree mode requires null revisions in every non-null slot. Committed mode requires an explicit full lowercase 40- or 64-hex commit SHA in every non-null slot and reads only the selected exact tree; it never infers HEAD or fetches. The default owner's identity is explicit when its slot exists. Shapes of all supplied slots are validated, but only the selected slot's contents are opened. Binding-shape diagnostics identify only the generic slot name (`project`, `company`, or `default`) and never echo a repository ID from the private map.

The selected definition is an exact object with `schema_version`, `id`, `name`, `owner`, `tokens`, `components`, `assets`, and `contrast_pairs`. Owner is exactly `{level,id}`; level is `project|company|default` and ID must equal the corresponding explicit context identity. Tokens have exactly `id`, `type`, and one present key, `value` or `ref` (both keys being present is invalid even if one is null). Literal types are opaque `color` (`#RRGGBB`), finite JSON `number`, or bounded nonempty `string`; a reference resolves iteratively to a same-system, same-type token. Cycles, dangling references, invalid types, or values fail closed.

Components have exactly `id`, `name`, `documentation`, `token_ids`, `states`, `variants`, and `examples`. Variants have exactly `id`, `name`, `token_ids`. A contrast pair has exactly `foreground_token`, `background_token`, and numeric `min_ratio` from 1–21. Arrays are required and nonnull; at least one token is required. IDs are unique in their token/component namespaces and within component variant/state namespaces. Documentation, examples, and assets are safe root-relative paths. Asset/evidence collisions and duplicate declarations fail. The evaluator requires the declared file set to equal the discovered regular-file inventory; undeclared files and orphan directories fail. No asset/example is executed.

The root `guide.md` must be declared as component documentation or an asset. It must contain nonempty literal level-two sections `## Overview`, `## Foundations`, and `## Components`, exactly once and in that order, outside fenced code blocks. Other sections are unrestricted. The existing operation reports an actionable no-go diagnostic when this fails; guide bytes remain part of the same full inventory digest. This rule does not assess prose or visual quality.

Design System limits: 256 KiB definition, 2 MiB per regular file, 64 MiB aggregate, 2,048 files, 1,024-byte paths, 2,048 tokens, 256 components, 64 states and variants per component, and 256 contrast pairs. Declared opaque-color contrast uses WCAG relative-sRGB luminance and compares the unrounded ratio to each minimum. Zero declared pairs is valid and checks zero pairs; this is not a general accessibility certification.

The response is the existing operation-specific schema, with explicit Project/Company IDs, `target: "design-system"`, `authority_scope: "local_structure_only"`, mode/revision, `go|no_go`, complete inventory digest, one accepted definition or no items, diagnostics, selected level, redacted source identity/owner/definition/revision, raw `definition_digest`, contrast count, and `design_system_validation`. No-go has no accepted item or digest. The inventory digest includes the complete managed inventory using the same v1 record encoding with source ID equal to `repository_id`; `definition_digest` is only SHA-256 of raw definition bytes. Downstream references use the full inventory digest, never the raw definition digest. A Prototype's reference is version binding only and does not prove that its implementation uses the system.

## Knowledge freshness, packets, and review authority

Knowledge `status` reports Project-local Landing and Roadmap states with authority `local_review_only`. Landing's required inputs are `project_mandate.md`, `domain_entities.md`, `project_constitution.md`, and `system_roadmap.md`; it also includes regular Markdown files under `policies/` and `modules/`, recursively, excluding any path segment named `tmp`, `temp`, or `generated` (case-insensitive). Roadmap includes only Markdown (`.md` or `.markdown`, case-insensitive) files under `todos/`, excluding `todos/ephemeral/` and any path segment named `tmp`, `temp`, or `generated`. Hidden files are included. Landing input digests include file content; Roadmap digests include only paths, so TODO body edits do not affect them, while path create/delete/rename can.

Knowledge v1 source digest is SHA-256 over sorted records. Each record writes a 4-byte big-endian UTF-8 path-byte length, then path bytes; Landing then writes the 32 raw bytes of SHA-256 over the file, while Roadmap writes no content digest. There is no domain prefix. Paths are unique, validated, and sorted by UTF-8 byte order. Status always reads fresh inputs and writes no snapshot or review marker.

The status response has exactly `schema_version`, `project_id`, `authority_scope`, `landing`, and `roadmap`. Each target state has `status`, `reason_code`, `observed_source_digest`, `reviewed_source_digest`, `observed_document_digest`, and `reviewed_document_digest`; digest values are `sha256:<64 lowercase hex>` or explicit JSON `null`. Status values are `current`, `review_required`, or `unverifiable`; reason codes distinguish `match`, `review_missing`, `source_changed`, `document_changed`, `source_and_document_changed`, and invalid/unavailable inputs. A valid marker's other target record does not confer a review on the selected target.

A `review-packet` binds target `landing|roadmap`, one committed Foundation revision (optional selector defaults to HEAD and resolves once to a full SHA), selected source inventory digest, output path (`project_landing.md` or `system_roadmap.md`), output-byte digest, and ordered inputs into the packet digest. Its exact JSON fields are `target`, `source_revision`, `source_digest`, `output_path`, `document_digest`, `inputs`, and `packet_digest`; an input is `{path,content_digest}`, with `content_digest` omitted for Roadmap. The binary digest hashes ASCII `builder-review-packet-v1`, NUL, five UTF-8 strings (`target`, revision, source digest, output path, document digest), each prefixed by 4-byte big-endian length; then a 4-byte input count and each sorted input's path and content-digest strings, each length-prefixed the same way. Roadmap content-digest strings are empty for packet hashing. Packet digest is `sha256:<64 lowercase hex>`. It emits complete packet JSON only. A packet is not human approval.

Only explicit `record-review` may write `knowledge_review.manifest.json`. The marker has exactly `schema_version: "1"`, `project_id`, `landing`, and `roadmap`; each target is null or an object with exactly `reviewed_source_digest`, `reviewed_document_digest`, `reviewed_packet_digest`, `reviewed_revision`, `reviewed_by`, and `review_reference`. It requires target, explicit full resolved revision, exact expected packet digest, reviewer label, and approval reference. A stored review revision is exactly a full lowercase 40- or 64-hex Git SHA; reviewer and reference must contain non-whitespace text. The complete serialized marker including its final newline cannot exceed 64 KiB. Under an exclusive marker lock it checks selected Git HEAD, exact committed packet, current working source inventory/output bytes, existing marker identity and semantic validity, then validates the full candidate marker before atomically replacing only that marker while retaining the other target record. Any rejection leaves marker bytes unchanged. Recording is an operator-authorized local record; it does not authenticate the reviewer or attest platform approval.

## Commands and results

Evaluator and knowledge operations require common `--workspace-root`, `--project-root`, `--foundation-root`, and `--project-id`. The separate `builder-project list` operation requires only an absolute `--state-root`; its other operations require the explicit context described below. Flag spelling, schema keys, and enums are exact; duplicate single- or double-hyphen flags, unknown options, positional leftovers, missing required flags, unsafe lexical paths, and invalid enum/SHA syntax are invocation errors.

| Command | Additional inputs | Success | Semantic/source rejection |
| --- | --- | --- | --- |
| `artifact-status prototypes` | `--mode working-tree|committed`; optional committed `--revision` selector (omission resolves HEAD) | Complete go JSON, exit 0 | Complete no-go JSON, exit 2; never partial accepted items/digest |
| `artifact-status design-system` | `--mode`, `--company-id`; optional `--source-bindings` and conditional `--default-owner-id`; configured pins are in map | Complete go JSON, exit 0 | Complete no-go JSON, exit 2; absent map uses only the standard Project binding, while a supplied missing/malformed map fails closed |
| `knowledge-status status` | None | Complete status JSON, exit 0 | Unsafe/unreadable/non-root Foundation: empty stdout, exit 2; stderr is sanitized and may be empty |
| `knowledge-status review-packet` | `--target`, optional `--revision` selector (default HEAD) | Complete packet JSON with resolved full SHA, exit 0 | Invalid source/revision/unsafe Foundation: empty stdout, exit 2; stderr is sanitized and may be empty |
| `knowledge-status record-review` | `--target`, explicit full `--revision`, `--expected-packet-digest`, `--reviewed-by`, `--review-reference` | Empty stdout, exit 0; selected marker only | Stale packet/HEAD/working bytes, wrong marker, contention or unsafe checkout: empty stdout, exit 2; stderr is sanitized and may be empty; no marker mutation |
| `builder-project list` | Absolute `--state-root` only | Sanitized Company/Project catalog JSON, exit 0 | Unavailable/corrupt state: exit 2 |
| `builder-project status` | Explicit Project context plus absolute `--state-root` | Registration state, stored Company identity, fresh local observations and last snapshot integrity, exit 0 | Binding mismatch is rejected; missing/unreadable source, changed source-bindings digest, unavailable state or corrupt saved snapshot: complete sanitized diagnostic JSON when the binding matched, exit 2; not-ready is never reported ready |
| `builder-project register` | Project context, state root, Project/Company IDs and names; optional `--source-bindings` and `--default-owner-id` | Registration and bounded immutable snapshot, exit 0 | Content preparation rejection is retained as not-ready with complete JSON, exit 2; conflicting identity or unavailable state fails closed |
| `builder-project decline` | Explicit Project context and state root | Context-bound optional-integration preference, exit 0 | Existing registration cannot be removed by decline; conflicting context fails closed |

Invocation errors use empty stdout, sanitized stderr, exit 64. Docker/bootstrap/build/output infrastructure errors use exit 70; consumers discard output on any nonzero infrastructure result. Knowledge semantic/source rejection uses empty stdout and exit 2, with sanitized stderr that may be empty; artifact semantic rejection emits its complete no-go payload and exit 2. Output write failures can leave partial bytes; nonzero infrastructure status means those bytes are never valid evidence.

## Ownership boundaries

`internal/source` owns bounded no-follow filesystem and exact Git tree access shared by both evaluators. `internal/codec` owns strict shared JSON primitives, not a schema registry. `internal/artifact_catalog` owns Prototype and Design System policy and hash domains. `internal/knowledge_status` owns Landing/Roadmap selection, packet and marker schema/hash policy. The two command packages own only their explicit flags, context adaptation and presentation; record-review keeps its specific lock and atomic writer. No generic command, persistence, provider, or schema framework is introduced.

The canonical English authoring skills are `skills/create-executive-landing`, `skills/create-design-system`, `skills/create-prototype`, and `skills/register-builder-project`; exact Claude/Cline mirrors provide discovery only. They link here for reusable schemas/operations and retain their distinct authoring method.

## Optional local Builder registration

`builder-project` is a local file-backed integration command, not an HTTP server, database, IAM boundary, publication mechanism, or Project URL verifier. Through the public launcher, `list` requires no Project checkout; `status`, `context`, `register`, and `decline` require only the relevant identities. `register` additionally takes `--project-name`, `--company-id`, and `--company-name`; API-owned context supplies the binding and may preserve the existing binding on an idempotent repeat. Registration never scans siblings, creates a Project, or infers Company identity.

The private `registry.json` stores Company/Project metadata and private source bindings; public `list` omits bindings and local paths. One nonblocking OS lock covers each complete state mutation, including preparation. Busy callers receive `registry_busy` and may retry safely. Registration identity is idempotent for the same Company and source context and conflicts on rebind. `decline` stores a preference only for an absent registration; it never unregisters or removes snapshots. Status/list are read-only.

Each admitted snapshot is a content-addressed immutable JSON record under `snapshots/<sha256>.json`; the fingerprint is SHA-256 over the exact serialized snapshot bytes. Limits are 128 KiB registry metadata, 2 MiB per file, 24 MiB decoded aggregate content, and 32 MiB serialized snapshot. Only evaluator-accepted/manifest-declared files are copied. Missing artifacts are pending; malformed existing artifacts are invalid; registration state, snapshot integrity, source-origin comparison, and human review remain distinct. During preparation/status, visual-origin observations compare only the Knowledge, Roadmap, or Design System digests whose declared encoding exactly matches the supported evaluator hash domain; incompatible or absent domains are `unverifiable`, and digest mismatch remains distinct from artifact availability. No origin is polled after preparation. Builder mounts the shared state read-only and serves only files declared available by a verified snapshot, using fingerprint-scoped routes so relative references remain within the same immutable snapshot. Rendering is local preview only, not review, visual-fidelity approval, or publication.

For a registered Project, `builder-project status` prepares fresh current artifacts and compares their admitted file bytes and stable artifact metadata with the verified saved snapshot. It ignores observation timestamps and the saved/current review and origin observations when deciding snapshot currency; those observations remain separately labeled. Equal current content is `ready`. A content/metadata mismatch returns complete JSON with `consumer_readiness: not_ready`, exit 2, a sanitized diagnostic, and `next_action` teaching an explicit matching `builder-project register` refresh followed by another status check. If changed current metadata marks an artifact invalid, status gives source-correction guidance before any refresh; unchanged pending/invalid artifacts do not independently block a matching snapshot. A targeted `--artifact-kind` status continues to report the fresh structural result for that artifact independently of saved-snapshot currency.

`builder-project status` is the producer-side source/snapshot currency check. The read-only Builder consumer cannot access mutable Project sources, so before reporting a saved available Prototype ready it requires a v3 Prototype status observation whose scenario projection matches the saved manifest alongside the Screen State data used by the viewer. A saved available v2 Prototype is hidden with migration-first TEACH; Landing and Design System remain usable. An incomplete v3 projection is rejected. No v2 compatibility reader is provided.

Prototype v3 `Related` is structural Foundation-root-relative evidence, not publication authority. Builder snapshot preparation admits only explicitly referenced, non-hidden Markdown files beneath the five canonical root documents or under `modules/`, `policies/`, and `todos/`, excluding `tmp`, `temp`, `generated`, and `ephemeral` segments. Approved-reference evidence must also be declared in `related`; it passes through this same safe filter and is copied into the immutable snapshot for its evidence link. Related evidence remains outside the Prototype inventory digest.
